# Разбор наброска и принятые изменения

Исходник: предоставленный `dh.go`. Приложение `main` — готовый Linux x86-64
ELF-файл, а не второй исходник. Он не запускался и не включён в новый проект.
Новая реализация собирается из исходного кода.

SHA-256 предоставленного `dh.go`:
`ae6807be2907a9ce8015f643f649d4dc975f2b57388c839592efffad2a25bcd0`.

| В наброске | В sai-dh |
| --- | --- |
| `big.Int` используется без импорта `math/big`, поэтому предоставленный текст не компилируется | Работа с ECDH через стандартный `crypto/ecdh` |
| `privateKey.D.Bytes()` даёт переменную длину | Приватный ключ всегда кодируется в 32 байта |
| Сырые `x.Bytes()` используются как AES-ключ; ведущий ноль может дать неправильную длину | Фиксированный результат ECDH, затем HKDF-SHA256 с солью, контекстом и привязкой к публичным ключам |
| AES-CFB не обнаруживает изменение сообщения | AES-256-GCM с аутентификацией сообщения и AAD |
| Функция `publicKeyToBitcoinAddress` возвращает hex HASH160 от ключа P-256 | Поле `fingerprint`: SHA-256 от публичного ключа; это не Bitcoin-адрес |
| HTTP без авторизации слушает все интерфейсы | Авторизация обязательна, по умолчанию слушается localhost |
| Ключи и ошибки обрабатываются прямо в HTTP-функциях | Отдельные криптографический пакет, сервисный слой, API и auth-провайдер |
| Не заданы границы размера и формат ошибок | Ограничения размеров, проверки полей/ключей, ошибки без копирования секретных входных данных |

Сохранена исходная кривая P-256. X25519, подписи, одноразовый блокнот, ratchet и
групповая криптография не добавлены под видом готовых возможностей.

## Изменения API

Это новая версия API с намеренно несовместимым форматом шифрования. Старые
CFB-сообщения не расшифровываются автоматически. Если существующие данные нужно
перенести, потребуется отдельная, явно запрошенная миграция с доверенным источником.

| Старый путь/поле | Новый путь/поле |
| --- | --- |
| `/generate-key-pair` | `/api/v1/keys/generate` |
| `address` | `fingerprint` — другой алгоритм и назначение |
| `/generate-dh-key` | `/api/v1/keys/derive`, обязательны `salt` и `context` |
| `shared_key` | `key` — результат HKDF, а не сырой секрет ECDH |
| `/encrypt` | `/api/v1/encrypt`, ответ — версионированный GCM-конверт |
| `/decrypt` | `/api/v1/decrypt`, принимает `envelope` и исходный `aad` |

Приватные ключи из наброска короче 32 байт нужно осознанно дополнить ведущими
нулевыми байтами до 32 при миграции. Новый API не принимает усечённое представление.
Публичные ключи остаются в формате P-256 SEC 1 uncompressed.

## Авторизация и граница доверия

В просмотренной реализации `sai-auth/pkg/providers/sai_auth_provider.go`
`extractRequestParams` читает тело исходного запроса, а отказ может сопровождаться
записью `request_params` в журнал. Такой адаптер не использован для ключей.
Новый адаптер отправляет пустой `request_params` и проверяет права на маршрут.
Это сохраняет HTTP-контракт sai-auth, не раскрывая ему криптографические данные.

HTTP-сервис имеет доступ к переданным приватным ключам и сообщениям. Он подходит
для доверенного сервисного контура или локального выполнения. Сквозное шифрование
будущего мессенджера требует выполнения криптографии на устройстве. Выделенный
пакет `pkg/dh` подготовлен для этого, но мобильные bindings пока не реализованы.

ECDH в этой версии не удостоверяет личность собеседника. Нужен отдельный
аутентифицированный обмен ключами/проверка отпечатков. Повтор корректного
шифротекста будет принят: учёт идентификаторов сообщений лежит на мессенджере.
Без свежих эфемерных ключей и соответствующего протокола нет обещания forward secrecy.

Итоги фактически выполненных проверок находятся в `VALIDATION.md`. Наличие
тестов в архиве не означает автоматически, что они были запущены.
